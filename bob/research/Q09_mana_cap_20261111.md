# Q09 Mana: cap by level and how it comes back

formula_finished false

A new Luther's mana cap is 20, the same dword as the current pool. There is no fixed cap for each level. Each crossing of the second bank adds 11, 12, 13, 14 or 15 to both the cap and the current pool. While he is alive and the pool is below the cap, the player tick adds the return of `0xE1A60`. For his starting form that argument is the cap shifted right by 2, which is 5. The seconds per point were not closed. No host. No piece.

## Cap

PROVEN for the stores. The new-game init stores 20 at `+0x141` (`0xCFB18`) and copies it to `+0x145` (`0xCFCFE`). Byte `+0x162` starts at 1 (`0xCFB00`).

`0xD8B94` is the second bank. It adds its argument to dword `+0x15D`. While byte `+0x162` is at most `0x1E` and the bank is at least dword `[index*4 + 0xE810]`, it subtracts that dword, increments the byte, and calls `0x12415C(0x221D8, 0, 0x9F)`. `0xD8C0E` shifts the return right by 5. `0xD8C17` adds 11. `0xD8C20` adds that sum to the cap. `0xD8C22` adds the same sum to the current pool. The loop jumps back, so one call can cross more than once.

Q03 entered the roll. Bound `0x9F` returns 0..159, and the shift leaves 0, 1, 2, 3 or 4, thirty-two values each. Plus 11 that is 11, 12, 13, 14 or 15. This note re-read the call and the add, not the roll body.

| Second index `+0x162` | Cap `+0x141` |
| --- | --- |
| 1, a new Luther | 20 |
| after one crossing | 31, 32, 33, 34 or 35 |
| after k crossings | 20 plus k draws of 11..15 |

The first bank, `0xD8A1C`, is the one that moves health, might and magic. It does not write `+0x141`. The thresholds themselves are the file image Q03 listed at `0x1CF834`. Index 1 costs 250 from the bank. The cap is not that 250.

## The tick

PROVEN for the body. From `0xD27C4` through the aura expiry at `0xD2CF9` there is no return, so this is the same player update. It reads health `+0x14D`. Zero skips the add. It then compares the cap with the current pool. If the cap is at most the pool, it skips. Otherwise the form byte `+0x1AB` picks the argument:

| `+0x1AB` | Argument to `0xE1A60` | At cap 20 |
| --- | --- | ---: |
| 2 | cap >> 1 | 10 |
| 1 | cap >> 3 | 2 |
| any other byte, including the 0 stored at `0xCFA77` | cap >> 2 | 5 |

`0xD280C` calls `0xE1A60(0x227A4, that argument)`. If word `+0x212` is nonzero, a second call adds more. The init stores 0 at that word (`0xCFB47`), so the second call is skipped for a new Luther. What later sets the word was not read.

If the sum of the returns is nonzero, `0xD285B` adds it to the current pool. `0xD286A` stores the cap when the sum would reach or pass it. `0xD2872` stores the sum when it is still below. `0xD28B2` then calls `0x7CE80` with the cap and the current pool. The two guards inside `0x7CE80` are the same ones Q08 left unread.

## What one return is

PROVEN as the arithmetic. `0xE1A60` reads controller `+0x505` and `+0x4B6`. With step `c` and those two dwords `p` and `d`:

- `a = ((p & 0xFFF) * c) >> 12`
- `b = (((p + d) & 0xFFF) * c) >> 12`
- if `a > b`, the return is `c - (a - b)`. Otherwise the return is `b - a`.

A full 4096-count advance of the summed input returns `c` altogether. For a new Luther that total is 5. It is not 5 on each visit.

`0xE0D01` stores the return of `0x14FA79` at `+0x505`. `0xE0CD2` stores `sar([ebx+0x4B0] + [ebx+0x52D], 16)` at `+0x4B6`. The word at `+0x4B4` is the same product shifted by 8 (`0xE0C82`). Q06's 1024-unit frame is that word. The dword beside it is that product shifted by 16, so a word of 1024 is a dword of 4, apart from the two different fraction slots (`+0x529` and `+0x52D`). Those are key-480 animation units and a raw timer read. `0xE1A60` adds them before the mask. Equating that sum to seconds was not done. The amount per second is UNKNOWN.

`0xD6A88` is a separate signed add of its second argument, clamped to the cap and to 0, then the same sync. Its callers were not listed. It is not this tick.

## The port

`player_starting_magic.gd` adds 1 to mana each `CAST_REGEN_SECONDS`, and `hive_magic_reward.gd` sets that constant to 3.0. The native argument at cap 20 is 5, passed through the 4096-count quantizer. The two rules do not agree.
