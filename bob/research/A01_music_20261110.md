Verdict: **DECODABLE**.

## Which path plays

The choice is one byte, not one byte per area. Object-5 dword `0x2238E` is four adjacent option bytes. Its high byte is `[0x22391]`. The filename builder at analysis `0xAD3C8` (file `0xE43C8`) does `sar edx, 0x18` on that dword and compares with 2.

| `[0x22391]` | what the builder does, if the player calls it |
| --- | --- |
| 2 | `MUSIC\<stem>.AUD` |
| 1, or any other nonzero value | `MUSIC\<stem>.HMI` |
| 0 | the builder is not called; the player takes the stop path |

The stem is `dword [index*4 + 0xD0E8]`. That table is object 5, file `0x1CE10C`. The index is the byte the caller passes. `call 0x150158` gets the destination, the format, and that stem. A zero index returns before the lookup. Slot 0 is the empty string at object-5 `0x125E`. Slots 1–34 are the stems above, so opcode 210 arm 0/1 byte 5 is the index.

The player entry is analysis `0xACFD0` (file `0xE3FD0`). The call at analysis `0xA0516` passes the record at `0x26D14`. Inside that function, analysis `0xAD300` builds a name from byte +0, which is the arm 0 byte. Analysis `0xAD29A` builds a name from byte +6, which is `0x26D1A`, the arm 1 byte. Both calls use the same type byte.

The options reader stores the type at analysis `0xCBC8F` (file `0x102C8F`). It reads `Audio_Music_Type` only when byte `[0xB868]` is nonzero. The image byte at file `0x1CC88C` is 1. The value `Off` stores 0. The value `Midi` stores 1. Any other value, including `Digital`, stores 2. If `[0xB86D]` is nonzero, the store is clamped to 0..1, so 2 cannot remain. `[0xB86D]` is cleared when `DMUSIC.MIX` opens (analysis `0x11A742`) and set to 1 when that open fails (analysis `0x11A74A`). Its image byte is already 0. `[0xB868]` is cleared by `-NOMUSIC` (analysis `0xA0154`) and, at analysis `0x11B191`, when the MIDI device field is -1 and `[0xB86D]` is already nonzero.

This install has `DMUSIC.MIX`, `OPTIONS.INI` says `Audio_Music_Type=Digital`, and `[0xB86D]` stays 0. The stored type is 2. Every arm 0/1 row in the table below is therefore `MUSIC\<stem>.AUD`. The HMI name is the same stem with type byte 1. No area has its own extension.

`Volume_Music` is stored at `[0x2238D]` (analysis `0xCBB2F`, the result of the `Volume_Music` read). Analysis `0xACFDB` compares that byte with 0 and leaves through the stop path. This install's `Volume_Music=0`, so the start function does not reach the filename builder while that byte stays 0. Raising it does not change the extension. The extension stays AUD.

## What the banks are

`MELODIC.BNK` and `DRUM.BNK` are 5404 bytes each. Both start `00 00 ADLIB-`, then u16 127, u16 127, u32 `0x1C`, u32 `0x61C`. Offset `0x1C` holds 128 records of 12 bytes (u16 index, one flag byte, then the name). The melodic names begin `PIANO1`, `PIANO2`, `PIANO3`, `HONKTONK`. Offset `0x61C` holds 128 records of 30 bytes, and `28+1536+3840` is the file size. That is an AdLib instrument bank. The 30-byte field layout was not entered, so calling each record an OPL patch stays LIKELY.

Each name has one fixup. Analysis `0x11B07E` loads `drum.bnk` and analysis `0x11B0C9` stores it at object-5 `0x109D60`. Analysis `0x11B0AA` loads `melodic.bnk` and analysis `0x11B0F9` stores it at object-5 `0x109D5C`. The same block receives the device id, port, IRQ, and DMA that the `DIGITAL` section parser filled, and analysis `0x11B124` passes the block to `0x1549BA`. The AUD filename builder does not reference either name. `SILENCE.AUD` is a third name in the following block (object-5 `0x3B16`), not a bank.

`TEST1.HMI` is 4118 bytes and starts `HMI-MIDISONG061595`. That signature is the string at object-5 `0x4D6C`. It is not one of the 34 stems. Drivers on disk, named from the same executable and not entered here: `HMIDET.386`, `HMIDRV.386`, `HMIMDRV.386`. A-02 owns playback. Nothing was converted.
